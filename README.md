# Najaf Accommodation

The hosted Worker serves both the web app and its API. A SQLite-backed Durable Object stores reservations, room inventory, settings, and sync history. The Worker talks directly to NKERP. A one-minute Cloudflare trigger runs the automatic pull and retention cleanup.

## Cloudflare deployment

From a Cloudflare-authenticated checkout use `npm run deploy:check`, then `npm run deploy`. Both run `scripts/deploy.mjs`, which also works in a Claude Code cloud session: it routes the cf CLI through the session's HTTPS proxy, which supplies the Cloudflare key. That proxy also replaces the one-time token Cloudflare's static-asset file upload needs, so in a cloud session the script builds first, packs the page files into the Worker bundle (`scripts/embed-assets.mjs`) and deploys that prebuilt output; the Worker serves them with the same single-page-app fallback. From a computer without the proxy the deploy uses Cloudflare static assets as before. `npm run test:deploy` checks the packed Worker. Pushing to GitHub does not deploy. Configure `NKERP_LOGIN_ID` and `NKERP_PASSWORD` as Worker secrets. The hosted app is publicly accessible and opens without a sign-in.

For the first deployment, temporarily set `NAJAF_IMPORT_KEY` to a separate random secret. Send the migrated database snapshot as JSON to `POST /api/admin/import` with that secret in the bearer header. The snapshot contains `reservations`, `rooms`, `history`, and `settings` from the Node app database. It may also contain `removed-stays`. The Worker accepts only the first import. Remove the import secret after verification.

## Optional local development

Use Node.js 24 or later.

```sh
npm install
cp .env.example .env
npm run dev
```

Set the NKERP account in `.env`, then open [http://127.0.0.1:3000](http://127.0.0.1:3000). For a production build, run `npm run build` followed by `NODE_ENV=production npm start`. The app stores changes in SQLite under `~/.local/share/najaf-accommodation` by default. Set `NAJAF_DATA_DIR` to use a different permanent directory. Working copies on the same computer use the same default database.

The app pulls Najaf applicant, stay, and room-allocation data from NKERP at startup and every minute while running. **Pull from NKERP** starts the same read-only refresh. A second request joins a pull already in progress. Profiles and stay dates come from the Najaf allocation search and tour accommodation plan. Current room assignments come from NKERP’s room-allocation records. NKERP’s allocated-room response supplies fewer profile fields than the applicant search, so previously saved values are preserved when the upstream field is absent.

The app keeps repeat trips separate by tour reference, guest, and arrival. When NKERP changes a stay's dates, the saved stay takes the new dates and keeps its room and app details, even when the new dates don't overlap the old ones. NKERP's new dates also replace an earlier date edit made in the app. An outdated copy of a moved stay is removed, unless it holds a room the current stay doesn't have yet, a star, a B→A shift or money given. Deleting a stay that NKERP still lists hides only that exact stay. If NKERP later changes its dates, it comes back. **Zaereen → More → Deleted NKERP stays** lists what is hidden and restores it. `GET /api/nkerp/tour?ref=<tour>` shows, read-only, what NKERP and the app each hold for one tour. Saves use the app database. The scheduled cleanup removes a stay and its sync history 72 hours after its departure time in Baghdad. A departure date without a time is retained through that date’s end before the 72 hours begin. Room inventory and settings persist independently. **Rooms → Add rooms** adds one room or a range of rooms to Burhani, Saifee or Badri with their beds, sleeping capacity, buffer, bed type, toilet, category, floor, features and notes. **Edit** on a room card changes those details later. New rooms are available straight away for allotment, switching, the timeline and the AI Planner. **Reset to 120 rooms** removes added rooms and restores the official specs. **Export room allocation** downloads the saved allocations and inventory as an Excel file.

**AI Planner** plans rooms for zaereen who have none yet, for the arrival dates you choose, using what it learns from the allocations saved in the app. Only one family shares a room; putting families together is a manual choice. A family is the group ID when there is one, otherwise the NKERP family number (F-1, F-2 … within a tour). Some tours give every zair their own family number; those zaereen are grouped by their shared HOF ID, and **Allot Room → Allot Entire Family** uses the same household. Family numbers that already hold several people are never merged through the HOF ID. Families stay together whenever one room can hold them, and the planner picks the room that leaves the fewest beds empty: an exact fit first, then a buffer bed, and only then a room with empty beds. Office and building habits only decide between rooms that fit equally well. A family no free room can hold is split into the two parts that leave the fewest beds empty. The summary shows the plan's empty beds. Starred zaereen always go to Burhani first; their remarks decide the exact room. Tours stay in one building, each office's usual buildings are preferred, and infants under 3 take no bed. Everyone in these hotels is Category A: zaereen shifted A→B are in external hotels and are left out, and anyone who doesn't fit can be shifted A→B from the planner. A zair NKERP lists twice on a tour is planned once. Change any room, split a family or untick tours, then **Refresh plan** to keep your changes and re-fit everyone else into the space left, and allocate in one save. Nothing goes to NKERP until you run **Sync to NKERP**. Run `npm run test:planner` for its tests.

**Allocation rules** apply automatically in the AI Planner and when allotting by hand. KUN HR keeps Badri 103, 104, 203, 204 and 205 for its big group and Badri 107 for its small group; no other office can be given them. Burhani 409, 410 and G2 stay empty until someone approves a prompt to use them. Saifee keeps 2-pax rooms for single-gender zaereen (gents on the 7th floor, ladies on the 1st; the counts are set in the planner), shared across tours by the same gender only, with Mohammedi for gents and Badri for ladies when they are full. Amatullah Aai Saheba Trust fills Saifee, then Badri, Mohammedi and Burhani, grouped by surname and using buffer beds. Staff can also type instructions into the planner's chat box ("Don't allocate Saifee 101", "Put <office> only in Saifee", "Allow Burhani 409"); they are saved with the app settings for everyone. The Zaereen page shows one row per ITS; a "+1 stay" tag lists the other records.

**Approvals** is the Nizam (Tour Admin) approval planner for Najaf and Karbala. It reads NKERP's new and re-approval queues, each Tour ID's chat box and previous city stays, and the accommodation dashboard every 15 minutes and on **Refresh from NKERP**. Hotel tours (Accommodation Required in Faiz = No) are planned on the exact chat dates and sequence; with only a sequence the days are split in that order and an odd day goes to Karbala. Faiz tours follow a chat request, otherwise the balanced split, and only the order is chosen for capacity. Each Tour ID shows its tour details, then four editable dates (Karbala arrival/departure, Najaf arrival/departure) that recalculate capacity at once. Najaf 290 and Karbala 400 Faiz pax are the default limits; tours still showing NKERP's dustbin sign are kept as a buffer. Outside the submission cut-off (15 days, or 30 in rush periods: a setting the planner follows) a dustbin tour waits for the Tour Operator; inside it the Tour ID is flagged for urgent follow-up and the approver is prompted to contact the Tour Operator. Once the dustbin sign disappears the tour goes through the normal approval. Whole Tour IDs only are shifted between Najaf-first and Karbala-first, with the before/after impact. Every re-approval is flagged and put on the admin's review list, compared with the previous approval (venue, subvenue, departure date, hotel and Faiz accommodation, other changes); it can be marked reviewed and keeps its history. **Only an unsaved itinerary blocks approval:** NKERP's fly mark (the Add/Edit Transport Itinerary icon) turns red once the itinerary is saved, and until then the Tour ID cannot be selected or approved. The dustbin sign, pending chat details, awaiting and re-approval status, and capacity are warnings shown in the confirmation, never restrictions (requests NKERP cannot take from the planner, such as missing city dates or a Preferred, linked or package tour, still have to be fixed first). Ready, re-approval, awaiting and pending-submission Tour IDs can all be ticked; the selection is shared across the lists and nothing is selected for you. **Approve in NKERP** or **Approve selected** sends one approval per Tour ID after a confirmation; a result that does not come back is never resent. Each Tour ID's NKERP chat box is shown with its history, and the admin can type a message (or start from a follow-up for the itinerary, subvenue dates, accommodation option or submission) and **Send to NKERP chat**: it goes to the real chat box in NKERP (`api/masters/saveChat`), the chat is read back, and the send is logged with the Tour ID; an unanswered send is never repeated automatically. The tab also has the Najaf-only daily report and the remaining-tours report with a suggested resolution for each, and drafts WhatsApp follow-ups (one per tour, or **WhatsApp follow-ups** for one message per office) to copy and paste.

**Approval → rooms chain:** NKERP lists a Najaf stay for room allocation once it is approved. A few days before it arrives (3 by default, set in the AI Planner; not earlier, so the rooms can still be used better), the app drafts rooms for it with the AI Planner, on the scheduled refresh. A tour's draft stays as it is until that tour changes: NKERP moves its dates, zaereen are added or removed, or another allocation takes a drafted room. Then only that tour is re-planned, and the AI Planner shows what changed and why. Drafts are never allocated on their own: **Apply** (or **Edit** to change rooms in the planner first), then **Sync to NKERP**. **×** sets a tour aside until NKERP changes it.

**B→A slip records:** every B→A slip printed or downloaded is recorded with its number, date, tours, zaereen and accounts note; reprints add to the same record. The list is under **B→A shifts**.

**Storage:** reservations, rooms, sync history, slip records and approval records are stored one SQLite row per record (`server/row-store.ts`), so a save writes only the records that changed. The first start after this change copies each old collection into rows and leaves the original value untouched as a backup.

**Sync to NKERP** still previews or applies deallocations, reallocations, and allocations from the saved app records using the existing Najaf allocation checks. The applied-run history lives in the app. Automatic pulls do not send allocation updates or emails.

## One-time migration for another installation

Stop the previous app. Export the live workbook as Excel. If the previous installation has a local `data/reservations.json` with app edits, provide its path to preserve app-only fields. The exporter abbreviates the grid tab name to meet Excel’s length limit.

```sh
npm run import:workbook -- /path/to/final-export.xlsx --legacy-reservations /path/to/old/reservations.json
```

Omit the legacy flag for a new installation. This command verifies the tabs and imports the grid, linked upgrade details, and allocation sync history in one transaction. The app derives its timeline from the saved bookings and seeds the same official inventory from its room definitions. Run the import against the same `NAJAF_DATA_DIR` as the new app. A successful import is recorded in the database, and repeating the same export returns its original result.
